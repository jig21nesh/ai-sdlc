# ADR-001 — keep filtering in domain and CSV delivery in web

Status: **proposed implementation decision under an existing accepted architecture constraint**. Actual acceptance owner/revision not supplied.

Context: I-9 revision 2 requests authorized invoice CSV export. The repository map assigns filtering to `src/domain/invoices.py`, parsing/streaming to `src/web/export.py`, and route tests to `tests/test_export.py`. Auth context carries `account_id`; domain modules may not import UI. No new vendor is allowed.

Recommendation: web obtains trusted auth context, calls the existing domain/billing boundary with that identity, and serializes/streams only the authorized result. Preserve domain ownership of filtering. Keep UI/HTTP/CSV-specific presentation details out of domain; do not assume an exact function signature until inspecting code. Retain the platform-pinned vendor SDK.

Alternatives: doing authorization filtering only in the UI cannot establish server-side isolation and violates the required boundary. Moving UI serialization into domain would couple domain processing to delivery and contradict the architecture owner's prohibition. A new export vendor is outside accepted scope. No such changes are proposed.

Consequences: domain and route checks must demonstrate account scoping; route/CSV checks must distinguish valid formatting from authorization. Keyboard behavior belongs to the actual UI entry point, which is not supplied. The design does not settle CSV dialect or spreadsheet interpretation; those are explicit decisions in SPEC.md.

Evidence limits: no source code or spike was executed. This is a repository-map-based design recommendation, not feasibility or performance proof. Existing billing pagination and streaming/error semantics need inspection. Revisit if the established billing boundary cannot enforce required scoping or consumer requirements change.
